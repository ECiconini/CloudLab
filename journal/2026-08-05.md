FINALIZAÇÃO DA ESTRUTURA CLOUDLAB:

Hoje dei continuidade à organização do meu laboratório. O principal objetivo era finalizar a estrutura do projeto, configurar o Git corretamente e publicar o CloudLab no GitHub utilizando boas práticas.

Inicialmente, organizei toda a estrutura de diretórios do projeto. Durante esse processo percebi que havia cometido um erro importante: eu havia criado todas as pastas (aws, docker, linux, docs, journal, etc.) diretamente dentro do diretório /home/ciconini, enquanto o repositório Git estava inicializado apenas dentro da pasta CloudLab.

Após analisar a estrutura, entendi que apenas o conteúdo localizado dentro da pasta que contém o diretório .git é versionado pelo Git. Para corrigir esse problema, movi toda a estrutura para dentro da pasta CloudLab, deixando-a como diretório raiz do projeto.

A estrutura final ficou organizada da seguinte forma:

CloudLab/
├── assets/
├── aws/
├── cheatsheets/
├── docker/
├── docs/
├── journal/
├── labs/
├── linux/
├── networking/
├── projects/
├── scripts/
├── terraform/
├── README.md
├── CHANGELOG.md
└── .git/

Essa organização vai servir como base para todo o restante do laboratório.

APRENDENDO COMO O GIT FUNCIONA:

Com a estrutura pronta, comecei a entender melhor o funcionamento interno do Git.

Até então eu imaginava que, ao criar um arquivo dentro do projeto, ele automaticamente passava a fazer parte do repositório. Durante os estudos compreendi que isso não acontece.

Aprendi que todo arquivo passa por um ciclo de vida antes de ser registrado no histórico do projeto.

O fluxo ficou claro para mim:

Arquivo criado -----> Untracked -----> git add -----> Staged -----> git commit -----> Histórico do Git

Também compreendi a função da Staging Area, que funciona como uma área intermediária onde escolho exatamente quais alterações serão registradas no próximo commit.

____________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________

MEU PRIMEIRO COMMIT:

Após entender o fluxo do Git, realizei o primeiro commit do projeto.

Esse momento foi importante porque marcou oficialmente o início do histórico do CloudLab.

Também aprendi a utilizar comandos como:

git status
git add
git commit
git log --oneline

Estou utilizando o git status constantemente antes de executar qualquer outro comando do Git, criando o hábito de verificar o estado atual do repositório antes de realizar alterações.

PROBLEMAS ENCONTRADOS DURANTE O PROCESSO:
Durante os testes encontrei um problema interessante.

Todo o laboratório havia sido criado utilizando o usuário root.

Quando passei a utilizar o usuário ciconini, não conseguia executar comandos do Git por falta de permissões.

Inicialmente pensei que fosse um problema do próprio Git, mas durante a investigação compreendi que os arquivos pertenciam ao usuário root.

Para corrigir isso alterei o proprietário de todo o laboratório utilizando: sudo chown -R ciconini:ciconini ~/CloudLab

Esse problema me ajudou a entender melhor a diferença entre:

proprietário do arquivo (Owner)
permissões do arquivo
usuário atual do sistema

Também aprendi a utilizar:

whoami
ls -la
chown (change Owner)

Além disso, ficou claro para mim que o ideal é utilizar sempre um usuário comum e recorrer ao sudo apenas quando realmente for necessário.

Depois de concluir a organização do projeto, criei um repositório público chamado CloudLab no GitHub.

Nesse momento aprendi conceitos importantes como:

Repositório Local
Repositório Remoto
Remote

Também entendi que o comando "git remote add origin" não envia nada para o GitHub. Ele apenas informa ao Git onde está localizado o repositório remoto.
Da mesma forma, aprendi que "git branch -M main" serve apenas para renomear a branch principal.

PROBLEMAS ENCONTRADOS AO TENTAR SUBIR O PROJETO PARA O GITHUB:

Ao tentar realizar o primeiro git push, encontrei um novo problema.

O GitHub recusou a autenticação utilizando usuário e senha.

Inicialmente imaginei que estivesse digitando alguma informação incorreta, mas durante a investigação descobri que o GitHub não aceita mais autenticação por senha para operações Git via HTTPS.

Essa foi uma descoberta interessante, pois me levou ao estudo de autenticação utilizando chaves SSH.

____________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________

CONFIGURAÇÃO DA CHAVE SSH:

Verifiquei que o diretório ~/.ssh possuía apenas o arquivo authorized_keys.

Como ainda não existia um par de chaves, gerei uma nova chave utilizando: ssh-keygen -t ed25519 -C "ECiconini"

Após a criação da chave, compreendi a diferença entre chave privada e chave pública

Cadastrei a chave pública no GitHub e alterei o repositório remoto para utilizar autenticação via SSH: git remote set-url origin git@github.com:ECiconini/CloudLab.git

Depois realizei o teste com o comando: ssh -T git@github.com
Recebi a mensagem de autenticação bem-sucedida, confirmando que a chave havia sido configurada corretamente.
